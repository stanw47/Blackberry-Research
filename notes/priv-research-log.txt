9. TOKEN / DAEMON DETAILS (bb_tokenserviced RE)
================================================================================
- Daemon serves /dev/socket/tokenservice; uid 519 token_service.
- Protocol (DataOutputStream, big-endian):
  0x01 GET(name):      writeInt(len)+name, read payload         (handler 0x3e60)
  0x02 WRITE(token):   writeInt(size)+token, read 1 byte resp   (handler 0x3f7c)
  0x03 ERASE_ALL:      writeInt(0), read                        (handler 0x4c84)
  Exactly 3 commands; default -> "unknown command: %c", close fd.
- Write handler 0x3f7c-0x4c00: max token size 0x876 (2166).
  Parse 0x58e4: {4B field0, 4B PIN, 40B BSN, 6B expiry, str1 NUL, str2 NUL,
  sig tail}; requires size>0x38, str1 len<=0x40, str2 len<=0x400, sig<=0x400.
  NO signature verification, NO PIN/BSN checks in the daemon.
  Expiry check 0x545c: "000000"=never; else YYMMDD with YY+100 vs current
  date (0x5c64). "991231" -> 199 > 117 -> valid.
  State parse 0x53e4: str2 sets out[0x476]; "development" is what aboot gate wants.
- Token names whitelisted: hlos_unsigned.tkn, hlos_signature.tkn,
  sw_rollback.tkn, ddt.tkn.
- token_mfi.bin (96 B, correct for this plan):
  {0x00000000, PIN 0x2c3d3fe1, BSN "1161797525"+NULs, "991231",
   "hlos_unsigned.tkn", 'state="development"', "AAAA"}
  => aboot would read /nvuser/hlos_unsigned.tkn state=development -> skip image
  verification. Token CONTENT is not the problem; the WRITE permission is.

19. KERNEL LPE EXPLOIT DEBUGGING (SESSION 7A) - IN PROGRESS
================================================================================
Goal: binder UAF (CVE-2019-2215-class) to leak kernel heap pointers via pipe
  writev, then arb-write thread_info->addr_limit -> -1, disable selinux,
  cred overwrite -> root.

EXPLOIT GEOMETRY:
  1. open /dev/binder -> epoll_ctl(ADD) -> pipe() -> ioctl(BINDER_THREAD_EXIT)
     -> kfree(binder_thread) at X (kmalloc-512, 296B)
  2. Writer: writev(pipefd[1], iov, 24) -> rw_copy_check_uvector kmalloc(384) =
     kmalloc-512 -> SHOULD reuse freed binder_thread at X -> kernel copies 24
     iovecs to X
  3. Writer fills pipe (65536 bytes from iov[0]), blocks in pipe_wait
  4. Main: epoll_ctl(DEL) -> ep_remove_wait_queue -> remove_wait_queue ->
     list_del(&pwq->wait.task_list) -> writes X+0x50 to X+0x50 and X+0x58
     (corrupts iov[5].iov_base and iov[5].iov_len)
  5. Main: throwaway read drains pipe -> writer wakes, copies remaining 512 bytes
     from corrupted iov[5] (base=X+0x50, len=X+0x50)
  6. Data from X+0x50 (kernel heap) should appear in pipe -> read it

RESULT: FAILURE - writev always returns 65536 (PIPE_CAPACITY), never 66048.
  The 512 bytes from corrupted iov[5] are never written.

DIAGNOSTICS:
  - Signals blocked in writer thread - no change
  - Timing confirms writer DID block and wake (406ms total)
  - FIONREAD confirms 0 bytes in pipe after throwaway read
  - No data even after 200ms+ wait

DISASSEMBLY (pipe_iov_copy_from_user @ 0xffffffc000315470):
  Two paths:
  - ATOMIC=1 (0x315578): __copy_from_user directly, NO addr_limit check
  - ATOMIC=0 (0x3154d0): manual addr_limit check via ldr x3,[x25,#8] (x25 = sp &
    ~0x3fff = thread_info). If iov_base + copy > addr_limit -> memset dest to zero,
    return -EFAULT. ALWAYS fails for kernel addresses.
  pipe_write retry: atomic=1 fails -> atomic=0 -> addr_limit check rejects kernel
    address -> -EFAULT -> since ret already 65536 > 0, error swallowed -> writev
    returns 65536.

UNRESOLVED: WHY does the atomic=1 path fail?
  __copy_from_user uses plain LDR (not LDTR), no access_ok. X+0x50 is in kernel
  direct map; page SHOULD be mapped/readable. Possible causes:
    (a) kmalloc(384) did NOT reuse freed binder_thread (some other allocation
        consumed the slot between kfree and kmalloc). iov[5] still base=NULL ->
        __copy_from_user(src,NULL,512) -> page fault -> -EFAULT.
    (b) CONFIG_DEBUG_PAGEALLOC enabled -> freed slab page unmapped -> can't read.
    (c) other page protection issue.
  Most likely (a): BINDER_THREAD_EXIT kfree -> writer kmalloc(384) gap lets other
  allocations consume the kmalloc-512 per-cpu freelist slot.
